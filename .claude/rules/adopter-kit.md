# The adopter kit

Three artifacts serve agents working on **apps that consume Pal** — never agents working on Pal itself. They are one source with two deliveries:

| Artifact | Role |
|---|---|
| `Documentation/ADOPTERS.md` | **canonical.** The brief adopters paste into their own `AGENTS.md`. |
| `plugins/pal-adopter/` | Claude Code delivery. Skills for app-side work; ships the brief through a **symlink**, never a copy. |
| `site/llms.txt` | Web delivery, generated by `docs.yml`. An index of links, never a copy. |

**Nothing here restates the brief.** A second copy of that content is the defect this layout exists to prevent — if you find yourself explaining mechanisms-vs-values or the `Loader` shape in a skill body, link to the brief instead.

**Nothing here carries Pal's contributor rules.** "Never add a dependency", "this is published API", the clean-code rules — those govern this repository, and leaking them to an adopter tells them to follow rules about a codebase they are not editing. The brief's job is the opposite: it shows adopters how to keep those rules *out* of their app.

## After any edit here

```bash
Scripts/check-adopter-kit.sh
```

It verifies the brief's version stamp, the plugin `version` that triggers `/plugin update` for installed adopters, the symlink, and the marketplace entry. A stale plugin `version` is silent: adopters keep the cached copy and never see the change.

Keep the brief short. It gets pasted into an app's own instruction file, where it competes with that app's rules for the same budget.
